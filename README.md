# Performance Workspace

เว็บสาธิตการประเมินผลงานและติดตาม KPI ใช้ React, TypeScript และ Vite

## หลักเกณฑ์สำหรับรอบประเมินประจำปี

ส่วนนี้อธิบายหลักเกณฑ์ของ prototype ใช้ระดับ 1–5 ร่วมกันทั้งองค์กร โดยกำหนดเป้าหมายราย KPI และเทียบหลักฐานของพนักงานตามกลุ่มงานและระดับตำแหน่ง

ก่อนเปิดรอบ HR เผยแพร่เป้าหมาย ผู้ประเมิน เกณฑ์ราย KPI น้ำหนัก หลักฐานที่ต้องใช้ และกำหนดส่งให้พนักงานเห็น หากเป้าหมายเปลี่ยนระหว่างรอบ ให้เก็บทั้งเวอร์ชันเดิมและเวอร์ชันใหม่ พร้อมเหตุผล วันที่มีผล และการรับทราบของพนักงาน

| ระดับ | ผลลัพธ์งาน | พฤติกรรมการทำงานที่สังเกตได้ |
|---|---|---|
| 1 ต้องปรับปรุงมาก | พลาดเป้าหมายสำคัญซ้ำและมีผลกระทบชัดเจน | ละเลยข้อตกลงสำคัญซ้ำ แม้ได้รับการติดตามและการสนับสนุน |
| 2 ต่ำกว่าคาดหวัง | ผลงานยังไม่ถึงเกณฑ์ของตำแหน่ง มีช่องว่างที่ระบุได้ | ทำตามข้อตกลงได้บางส่วน ต้องมีคนติดตามบ่อย |
| 3 ตามคาดหวัง | ส่งมอบงานตามเป้าหมายและเกณฑ์คุณภาพ | ทำตามข้อตกลง สื่อสารความเสี่ยง และส่งต่องานได้ตามมาตรฐาน |
| 4 สูงกว่าคาดหวัง | ผลงานเกินเป้าหมายและมีผลดีที่ตรวจสอบได้ | แก้ปัญหาเชิงรุกและช่วยให้ทีมส่งมอบงานได้ดีขึ้น |
| 5 โดดเด่น | ผลงานเกินเป้าอย่างมีนัยสำคัญและมีผลกระทบต่อเนื่อง | สร้างวิธีทำงานที่ผู้อื่นนำไปใช้ซ้ำได้และมีหลักฐานว่าได้ผล |

**วิธีคิดคะแนนสาธิต** ให้ผลลัพธ์งาน 70% และพฤติกรรม 30% โดยผลลัพธ์งานมาจากค่าเฉลี่ยถ่วงน้ำหนักของระดับ KPI และน้ำหนัก KPI รวมกันเท่ากับ 100% ส่วนหัวหน้าให้คะแนนพฤติกรรมตามตารางพร้อมตัวอย่างที่ตรวจสอบได้ คำนวณ `ผลรวม = ผลลัพธ์งาน × 0.7 + พฤติกรรม × 0.3` แล้วแปลงเป็นระดับด้วยจุดแบ่ง 1.5, 2.5, 3.5 และ 4.5 โดยค่าที่ตรงจุดแบ่งเข้าระดับสูงกว่าและใช้ค่าก่อนปัดเศษ สัดส่วนและจุดแบ่งนี้เป็นค่าตั้งต้นสำหรับการสาธิต

ตัวอย่าง KPI เวลาตอบกลับที่ยิ่งต่ำยิ่งดี เป้าหมาย 24 ชั่วโมง กำหนดระดับ 5 ที่ไม่เกิน 8 ชม. ระดับ 4 ที่มากกว่า 8 ถึง 16 ชม. ระดับ 3 ที่มากกว่า 16 ถึง 24 ชม. ระดับ 2 ที่มากกว่า 24 ถึง 36 ชม. และระดับ 1 ที่มากกว่า 36 ชม. KPI ที่ยิ่งสูงยิ่งดีใช้ช่วงในทิศทางตรงกันข้าม โดยทุกช่วงต้องครอบคลุมค่าที่เป็นไปได้และไม่ซ้อนกัน

**หลักฐานและการทบทวนคะแนน** พนักงานแนบผลจริง ช่วงเวลาที่วัด และหลักฐานต่อ KPI หัวหน้าอ้างอิงเหตุการณ์และผลกระทบที่สังเกตได้ตลอดรอบ HR เทียบกรณีในกลุ่มงานและระดับใกล้กันตามเกณฑ์เดียวกัน โดยตรวจคะแนนระดับ 1–2 และ 4–5 รวมถึงกรณีที่ผลลัพธ์กับพฤติกรรมต่างกันตั้งแต่ 2 ระดับขึ้นไป ก่อนยืนยันผล HR บันทึกคะแนนเสนอ คะแนนสุดท้าย ผู้ทบทวน วันที่ เหตุผล และหลักฐานที่ใช้อ้างอิง การกระจายคะแนนใช้ชี้กรณีที่ควรตรวจ และไม่มีโควตาบังคับรายทีม

**การแสดงผล** หลังยืนยันและเผยแพร่ ระดับ 4–5 แสดงว่า «สูงกว่าความคาดหวัง» พร้อมผลงานเด่นและโอกาสต่อยอด ระดับ 3 แสดงว่า «ตามความคาดหวัง» พร้อมข้อเสนอแนะ และระดับ 1–2 แสดงว่า «ต่ำกว่าความคาดหวัง» พร้อมช่องว่าง การสนับสนุนที่ตกลงกัน และวันติดตาม หากขาดหลักฐานที่จำเป็น ให้พักผลเป็น «ยังประเมินไม่ได้» และระบุสิ่งที่ต้องเติม การมาสาย การลา และการเลยกำหนดส่งไม่หักคะแนนอัตโนมัติ HR จัดการกำหนดส่งแยกจากผลประเมินและบันทึกเหตุผลเมื่อขยายเวลา

| กรณีตรวจรับ | ผลที่ต้องได้ |
|---|---|
| KPI ได้ระดับ 5 และ 3 น้ำหนัก 60/40 พฤติกรรมระดับ 4 | ผลลัพธ์งาน 4.2 คะแนนรวม 4.14 และเสนอระดับ 4 |
| คะแนนครบและหลักฐานรองรับผลต่ำกว่าเป้าหมาย | หลัง HR ยืนยัน แสดงช่องว่าง การสนับสนุน และวันติดตาม |
| KPI สำคัญขาดหลักฐาน หรือหัวหน้าส่งช้า | พักผลหากหลักฐานขาด และแสดงสถานะล่าช้าแยกจากระดับผลงาน |
| HR เปลี่ยนผลเสนอจากระดับ 4 เป็น 3 | ประวัติแสดงทั้งสองระดับ พร้อมเหตุผลและหลักฐาน ก่อนพนักงานเห็นผลเผยแพร่ |

## เริ่มใช้งาน

ใช้ Node.js 22.12 ขึ้นไป แล้วรันจากโฟลเดอร์โปรเจกต์บน Windows

```sh
npm.cmd ci
npm.cmd run dev
```

เปิด http://127.0.0.1:3000 คำสั่งนี้เปิด Frontend ที่พอร์ต 3000 และ Backend ที่พอร์ต 3001 พร้อมกัน ใช้ `npm.cmd start` ได้เช่นกัน กด Ctrl+C เพื่อหยุดทั้งสองฝั่ง

แต่ละหน้ามี URL สำหรับเปิดซ้ำหรือใช้ปุ่ม Back และ Forward เช่น `/hr/reviews/round-1/manager-comparison` เลขรอบเริ่มจากรอบแรกและใช้กับลิงก์เดิมได้หลังสร้างรอบใหม่ เมื่อโฮสต์ไฟล์จาก `frontend/dist/` ให้ตั้งค่าโฮสต์ให้ส่ง `index.html` สำหรับ URL ของหน้าที่เปิดโดยตรง และส่ง `/api` ไปยัง Backend

## โครงสร้าง

```text
frontend/
  src/components/           หน้าภาพรวม หน้ารายบุคคล และฟอร์ม
  src/domain/               เกณฑ์และขั้นตอนประเมิน
  src/services/             เชื่อม API และอ่านข้อมูลเดโมจากเบราว์เซอร์เดิม
  vite.config.ts            การตั้งค่า Frontend และ proxy ของ API
  workflow-check.mjs        ทดสอบการแสดงผลและขั้นตอนประเมิน
backend/
  src/server.mjs           Node.js HTTP API
  src/workspace-store.mjs  บันทึกข้อมูลและตรวจรุ่นก่อนเขียน
  data/workspace.json      ข้อมูลที่ API สร้างเมื่อเริ่มใช้
  test/                   ทดสอบ API และการบันทึก
scripts/dev.mjs            เปิดทั้งสองฝั่งจากโฟลเดอร์โปรเจกต์
```

เพิ่มสูตรการประเมินใน `frontend/src/domain/` และการเชื่อมต่อแหล่งข้อมูลใน `frontend/src/services/`
เก็บข้อความภาษาไทยเป็น UTF-8

## ตรวจสอบ

```sh
npm.cmd run check
npm.cmd test
```

`check` ตรวจชนิดข้อมูลและไวยากรณ์ ส่วน `test` ตรวจขั้นตอนประเมิน การเริ่มข้อมูลครั้งแรก การบันทึกหลังรีสตาร์ต และการป้องกันการเขียนทับจากข้อมูลรุ่นเก่า

แต่ละบทบาทมีหน้า «ภาพรวม» ของตัวเอง Employee เห็นสถานะ KPI และสิ่งที่ต้องทำต่อ Manager เห็นคิวอนุมัติและให้คะแนนของทีม HR เห็นความคืบหน้าทั้งองค์กร ค้นหาและกรองรายทีม รวมถึงส่งออก CSV ได้

เลือก «ภาษา / Language» ที่แถบด้านบนเพื่อสลับไทยหรืออังกฤษ เมนู สถานะ ฟอร์ม วันที่ และหัวคอลัมน์ CSV ใช้ภาษาที่เลือก แอปจะจำภาษานี้เมื่อเปิดในเบราว์เซอร์เดิม ชื่อคนและข้อความที่ผู้ใช้บันทึกจะแสดงตามต้นฉบับ

ในหน้า «ภาพรวม» ของ HR กดการ์ดแผนก แล้วเลือก «ดูลูกทีม» ของ Manager คนที่ต้องการ ตารางแสดงสถานะแผน KPI ความครบของข้อมูล ผู้รับผิดชอบ และสิ่งที่ต้องทำต่อ CSV ส่งออกรายชื่อที่เห็นหลังกรอง พร้อมชื่อรอบและกำหนดงานถัดไป หากต้องติดตามงาน Manager ข้ามแผนกให้เปิด «งานค้างทุกทีม»

ข้อมูลสาธิตมี 3 แผนก แผนกละ 2 Manager และพนักงานรวม 22 คน เช่น Operations คนที่ 1 ดูแล E101–E105 ส่วนสุภาวดี แก้วใส ดูแล E106–E108 เมื่อสลับเป็น Manager ให้เลือกทั้งแผนกและชื่อ Manager เพื่อดูคิวงานและ feedback ของลูกทีมตนเอง KPI กลางยังใช้ร่วมกันทั้งแผนก โดย Manager คนที่ 1 เป็นผู้แก้แผนกลาง

ก่อน HR เปิดรอบ ให้สลับเป็น Employee เลือกณิชา (E101) แล้วกด «อัปเดต KPI» เพื่อบันทึกผลจริง ช่วงเวลาที่วัด หลักฐาน และอุปสรรคได้หลายครั้ง Manager ทีม Operations เปิด «ติดตามผลงานทีม» เพื่อดูประวัติรายคนได้ ลอง E102 เพื่อดูตัวอย่างที่มีประวัติแล้ว

เมื่อ HR เปิดรอบ ระบบส่งแผนจากแม่แบบตามตำแหน่งให้พนักงานที่ยังไม่มีแผน สำหรับรอบที่เปิดอยู่แล้ว HR กด «ส่งแผนจากแม่แบบ» จากหน้าตั้งรอบ หรือตามลิงก์ «ดูคนที่ยังไม่มีแผน KPI» เพื่อจัดแผนรายบุคคล พนักงานตรวจเป้าหมาย น้ำหนัก เกณฑ์ และแหล่งข้อมูลใน «KPI และผลงานของฉัน» แล้วกด «ยอมรับแผน KPI» ก่อนส่งแบบประเมิน

HR แก้แม่แบบ Operations Specialist ได้จาก «เกณฑ์การประเมิน → แม่แบบ KPI ตามตำแหน่ง» และระบุเหตุผลเมื่อปรับแผนรายบุคคลจากแม่แบบ ระบบเก็บเลขฉบับและเกณฑ์ไว้กับแผนที่ส่ง ในรอบใหม่ E101 และ E108 รับแม่แบบเดียวกันแม้อยู่ใต้ Manager คนละคน Manager ดูสถานะแผนและตรวจหลักฐานของลูกทีมก่อนให้คะแนนพฤติกรรม

ในรอบสาธิต สลับเป็น Employee E101 แล้วเปิด «KPI และผลงานของฉัน» ในส่วน «ผลงานจากระบบงานจำลอง» กดดูรายการต้นทางเพื่อเทียบกำหนดส่งกับเวลาส่งครั้งแรกและเปิดดูผลตรวจ งานที่ถึงกำหนดในช่วงที่วัดใช้คำนวณสัดส่วนส่งทัน ส่วนอัตราผ่านครั้งแรกเป็นข้อมูลประกอบและแสดงจำนวนงานที่ยังรอตรวจ

กด «ใช้ผลกับ KPI» เพื่อบันทึกอัตราส่งทันเป็นผลจริงของ KPI «ส่งมอบงานตามกำหนด» ระบบเทียบผลกับเกณฑ์ที่ตกลงไว้และเก็บสำเนารายการต้นทางให้ Manager และ HR ตรวจย้อนกลับได้ ข้อมูลตัวอย่างมาจากชุดจำลองภายในโปรเจกต์

สำหรับทดลอง flow ประเมิน ให้เปิดรอบในบทบาท HR แล้วกลับไปที่ Employee E101 ข้อมูลที่บันทึกไว้จะแสดงต่อเนื่อง เมื่อ KPI ทั้งสองมีผลจริง ช่วงเวลาที่วัด และหลักฐานครบ ให้ส่งผลงาน สลับเป็น Manager ทีม Operations เพื่ออนุมัติงานก่อนให้คะแนนพฤติกรรม แล้วสลับกลับ HR เพื่อทบทวนมาตรฐาน ยืนยันหรือปรับคะแนน และเผยแพร่ผล พนักงานเปิดผล รับทราบ หรือขอทบทวนได้

ในต้นแบบนี้ HR ไปที่ «ตั้งรอบประเมิน» แล้วกด «ปิดรอบประเมิน» ได้ทันทีหลังเปิดรอบ หน้าต่างยืนยันแสดงจำนวนผลที่ยังไม่เผยแพร่และคำขอทบทวนที่ค้าง ระบบเก็บสถานะเดิมพร้อมล็อก KPI งาน และคะแนน พนักงานยังดูและรับทราบผลที่เผยแพร่แล้วได้ และ HR ยังดูรายละเอียดและส่งออก CSV จากหน้าภาพรวมได้

หลังปิดรอบ HR กด «สร้างรอบใหม่» จากหน้าเดียวกันเพื่อเริ่มฉบับร่าง ระบบนำรายชื่อพนักงาน ผู้ประเมิน และน้ำหนักคะแนนมาเป็นค่าเริ่มต้น ส่วน KPI งาน และผลประเมินเป็นของแต่ละรอบ กรอกชื่อรอบและกำหนดส่ง ตรวจทีมที่เข้าร่วม แล้วกด «เปิดรอบประเมิน» เลือกรอบจากเมนูด้านบนเพื่อดูประวัติรอบก่อนหน้า

Manager มีเวลาอนุมัติ 7 วันปฏิทินนับจากวันที่พนักงานส่งตามเวลาไทย โดยแยกจากกำหนดให้คะแนน พนักงานที่ส่งทันจะไม่ขึ้นว่าเลยกำหนดระหว่างรอหรือหลัง Manager อนุมัติ หาก Manager ไม่อนุมัติ ต้องระบุเหตุผลและส่งกลับให้แก้ไข ระบบจึงตรวจว่างานเลยกำหนดส่งเดิมหรือยัง การส่งใหม่เริ่มรอบอนุมัติ 7 วันอีกครั้ง

หลังเปิดรอบ Manager เลือก «ประเมินตนเอง» และ Employee เลือก «ให้ feedback ต่อ Manager» ทั้งคู่ตอบคำถามชุดเดียวกันหนึ่งครั้งต่อรอบ HR เห็นผลรวมของลูกทีมเมื่อมีอย่างน้อย 3 คนตอบ หากค่าเฉลี่ยต่างกันตั้งแต่ 1 คะแนนจาก 5 หรือคะแนนพนักงานไม่มีหลักฐานประกอบ HR ต้องบันทึกความเห็นผู้ทบทวนคนที่สองก่อนยืนยันระดับสุดท้าย คะแนน Manager เดิมยังอยู่และผลรวม feedback ไม่ถูกนำมาคูณคะแนนพนักงาน

สำหรับเดโม ลองให้ Manager คนที่ 1 ของ Operations ตอบ 5 ทั้งสามข้อ และสลับเป็น E101, E102 และ E103 ให้คะแนน 2 ทั้งสามข้อ จากนั้นเปิด «ทบทวนวิธีประเมิน Manager» ในบทบาท HR และเปิด E103 จากหน้าทบทวนมาตรฐานคะแนนเพื่อบันทึกความเห็นคนที่สอง หน้า HR แสดงผลรวมและจำนวนผู้ตอบ

ในหน้า «ทบทวนวิธีประเมิน Manager» เลือกกลุ่ม Operations Specialist เพื่อดูการกระจายคะแนนพฤติกรรม 1–5 และจำนวนที่ส่งแล้วของ Manager แต่ละคน กดแท่งคะแนนหรือ «ดูเคสที่ปรับระดับ» เพื่อกรองรายการ แล้วกด «ดูหลักฐานและเหตุผล» เพื่อเปิดผลรายคน กราฟก่อน–หลังใช้เฉพาะเคสที่มีทั้งระดับเสนอและระดับที่ HR ยืนยัน เช่น E108 ในข้อมูลสาธิตเริ่มต้นที่ปรับจากระดับ 4 เป็น 3

กรณีสาธิตเพิ่มเติม ได้แก่ E104 (ผลงานสูง) และ E105 (ผลงานต่ำ) ในคิวทบทวน, E102 (หัวหน้าเลยกำหนด), E204 (คะแนนสองมิติต่างกันสองระดับ) และ E304 (หลักฐานไม่ครบ) การเตือนเป็นการจำลองในแอป การเปลี่ยนเวอร์ชันเป้าหมายระหว่างรอบยังเป็นข้อกำหนดสำหรับการพัฒนาภายหลัง

จากหน้าทบทวนมาตรฐานคะแนน เปิด E104 และ E105 แล้วกด «ยืนยันหรือปรับระดับ» กรอกชื่อ HR เลือกหลักฐานที่ใช้ตัดสินใจ และบันทึกเหตุผล จากนั้นเปิด «ภาพรวมระดับผลงาน» แล้วเลือกทีม Operations และตำแหน่ง Operations Specialist เพื่อเทียบผลที่ยืนยัน ดู KPI ที่ต่างจากระดับ 3 มากที่สุดหลังถ่วงน้ำหนัก และเปิดประวัติการตัดสินใจรายคน ข้อมูลหลักฐานที่บันทึกพร้อมการตัดสินใจยังเปิดดูได้ในรอบที่ปิดแล้ว

## ข้อมูลและการนำขึ้นโฮสต์

Backend เก็บรอบประเมิน แผน KPI ผล และประวัติไว้ใน `backend/data/workspace.json` ครั้งแรกที่เซิร์ฟเวอร์ยังไม่มีข้อมูล Frontend จะนำข้อมูลจาก `localStorage` ของเบราว์เซอร์และ URL ที่เปิดอยู่มาเริ่มต้น หากไม่มีข้อมูลเดิม แอปใช้ชุดเดโม เมื่อเซิร์ฟเวอร์มีข้อมูลแล้ว ให้โหลดหน้าใหม่เพื่อเห็นรายการที่บันทึกจากแท็บอื่น

API ตรวจสอบสถานะที่ `GET /api/health` อ่านข้อมูลที่ `GET /api/workspace` และบันทึกที่ `PUT /api/workspace` การบันทึกใช้ `ETag` กับ `If-Match` เพื่อป้องกันการเขียนทับจากข้อมูลรุ่นเก่า

แอปเปิดบนเครื่องเดียวเป็นค่าเริ่มต้น และใช้ตัวสลับบทบาทสำหรับข้อมูลเดโม การใช้งานกับข้อมูลพนักงานจริงต้องมีการเข้าสู่ระบบและกำหนดสิทธิ์ที่ฝั่งเซิร์ฟเวอร์

ใช้ `npm.cmd run build` เพื่อสร้างไฟล์ใน `frontend/dist/` แล้วใช้ `npm.cmd run preview` เพื่อตรวจ build พร้อม Backend ในเครื่อง เมื่อนำไปโฮสต์ ให้ตั้ง reverse proxy จาก `/api` ไปยัง Backend
